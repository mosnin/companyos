# Evolve Company Capability

Turn an accepted opportunity into a typed candidate program. This skill plans
an improvement; it does not execute candidates, create tasks, schedule work,
install skills, call a model or provider, change a database, or promote a
result.

## Compile the program

1. Start from the accepted Company OS objective, mandatory requirements,
   baseline digest, authority decision, evidence, and measurable outcome. An
   unnamed new feature is valid when it is expressed as a bounded hypothesis
   with success and falsification criteria. Do not redirect innovation into
   maintenance merely because no feature name exists yet.
2. Choose one bounded target intent. The v2 compiler derives exactly three
   differentiated profiles (`conservative`, `adjacent`, and `first_principles`).
   Read
   [references/improvement-contract.md](references/improvement-contract.md)
   for the request contract and [assets/profile-registry.json](assets/profile-registry.json)
   for the supported strategy profiles.
3. Bind source and mechanism coverage, task-local capability IDs, the
   dependency-derived manager plan, member-level four-partition manifests, the
   evaluator-method resolution, independent roles, finite budgets, lifecycle
   cancellation/retry/dead-letter contracts, one authority/scheduler/evaluator/
   promotion chain, rollback, and delayed outcome.
4. Compile without side effects:

   ```bash
   python3 scripts/compile_improvement_program.py request.json --output program.json
   ```

5. Replay the exact request and verify the canonical output before manager
   dispatch:

   ```bash
   python3 scripts/compile_improvement_program.py request.json --verify-output program.json
   ```

6. Bind the program digest into the existing `$manage-company-program`
   charter. Existing master, manager, Luna worker, capability, authority,
   cancellation, verification, and integration controls remain authoritative.

## Non-negotiable boundaries

- Exactly one Company OS control plane, scheduler, evaluator registry, and
  promotion registry remain authoritative.
- Strategy adapters propose only. They cannot schedule, score, accept, promote,
  widen authority, or mutate governance.
- Discovery and adaptive validation may guide search. Sealed challenge and
  independent acceptance decide promotion. A challenge exposed or reused after
  feedback is burned.
- Candidate proposer, owner, evaluator, confirmer, accepter, and promoter are
  distinct. Candidate-supplied scores, registry pointers, credentials,
  readiness, partition members, or permissions are invalid.
- Memory, graph projections, sessions, realtime transport, and vendor callbacks
  are evidence or hints, never authority.
- Skills are task-local, content-addressed references. A capability cannot
  grant tools, installation, budget, or external effects.
- Missing evaluator readiness is a named blocker; missing telemetry remains
  unavailable and is never converted into a passing score or observed value.
- Promotion requires an atomic pointer, rollback, independent authority, and a
  later real-company outcome. Source acceptance is not runtime or production
  acceptance.

## Source boundary

Read [references/source-essence.md](references/source-essence.md) before
changing the profiles or mechanism registry. Public projects informed the
requirements; their runtimes are not dependencies. Multica and other custom,
unclear, noncommercial, or authority-colliding systems are clean-room design
evidence only. LiveKit is a separately authorized, project-local engineering
capability when a Company OS program is building a LiveKit application.
