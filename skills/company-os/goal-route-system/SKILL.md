# Goal Route Operating System

Treat the original user request as raw destination intent, not as an executable work packet.

The goal route system converts that intent into an operating model that every Company OS manager, submanager, and worker can act on without losing the root objective.

## Core model

```text
Operator context
        ↓
Concrete root goal
        ↓
Causal goal graph
        ↓
Reverse engineered route
        ↓
Route segments and sprints
        ↓
Manager goals
        ↓
Submanager goals
        ↓
Worker leaf goals
        ↓
Actions and environment evidence
        ↓
Goal progress and parent rollup
        ↓
Reroute or accept
```

The destination remains stable unless the operator changes it. Plans, sprints, owners, and local methods may change when evidence proves a better route is required.

## Kickoff profile

Compile the mission context before broad delegation. Capture or infer:

1. Autonomy mode and whether missing context should be researched or requested.
2. Customer, user, market, and business model.
3. Brand personality, visual direction, voice, and quality target.
4. Technical preferences, supplied repositories, existing systems, and prohibited replacements.
5. Time, token, cost, risk, and authority limits.
6. Required approvals and irreversible effect boundaries.
7. Existing assets, data, integrations, and known constraints.
8. Assumptions and unresolved questions.

When the operator authorizes autonomous operation, research missing context and mark assumptions explicitly. Do not silently transform assumptions into facts.

## Goal contracts

No agent is dispatched with only a prompt. Every owner receives a content addressed goal contract containing:

1. Goal, root, and parent identifiers and digests.
2. Owner role, agent template, level, and decision rights.
3. Purpose and contribution to the parent goal.
4. Evidence bound current state.
5. Observable target state.
6. Required state changes.
7. Success metrics.
8. Acceptance evidence.
9. Dependencies and route position.
10. Sprint, tasks, and subtasks.
11. Authority, write scope, budget, and deadline.
12. Constraints, non goals, cohesion contract, abort criteria, and fallback route.
13. Reporting and handoff destination.

A child may narrow the parent contract. It may not delete, invert, weaken, or replace a mandatory parent condition.

## Goal graph

The root goal represents the complete requested outcome. Manager goals own independently accountable causal branches. Submanager goals own bounded components. Worker goals own directly executable state transitions.

Every parent acceptance condition must be covered by at least one child contribution before decomposition is valid. Every leaf must be executable by one bounded worker. Goal graphs must remain acyclic and within declared depth and child limits.

## Route graph

Compile the route backward from the destination. The standard route contains:

1. Context resolution.
2. Strategy and system design.
3. First reality.
4. Capability expansion.
5. Integration and cohesion.
6. Verification and acceptance.

Each route node declares entry conditions, expected state transition, dependencies, owner, planned actions, verification, success branch, failure branch, degraded branch, rollback branch, reroute triggers, and exit conditions.

The route is executable state, not a roadmap essay.

## Sprints

Group ready route nodes into bounded sprints. A sprint contains one measurable sprint goal, exact child goals, tasks, subtasks, dependencies, artifacts, evidence, budget, deadline, and exit conditions.

A sprint does not complete because agents submitted reports. It completes when its target state is evidenced.

## Agent templates

Select the smallest established template that can own the goal. Presets include executive, product, technical, brand, creative, growth, sales, operations, supply chain, research, integration, quality, delivery submanager, engineering, design, research, creative, and operations worker roles.

A custom role may narrow a preset. It may not widen authority, budget, write scope, or accepted effects.

## Cohesion

Every goal inherits the shared cohesion contract covering customer promise, positioning, brand personality, visual language, product experience, copy, business model, technical principles, operational principles, cultural context, and acceptance quality.

Local optimization may not create a product, campaign, operation, or interface that contradicts the shared company identity.

## Evidence and progress

Advance goals only from bound environment evidence such as product artifacts, runtime behavior, browser journeys, database observations, integrations, campaign results, customer evidence, financial evidence, operational receipts, or independent evaluation.

Plans, source listings, manager confidence, worker completion messages, and internal narrative do not advance goal state by themselves.

Child completion rolls upward only when its declared causal contribution satisfies the parent condition.

## Rerouting and takeover

Reroute when assumptions fail, dependencies block, objective velocity stalls, runtime evidence contradicts the plan, a better route appears, or a manager or worker repeatedly fails.

Preserve the root goal, accepted evidence, passing artifacts, authority, budget history, and cohesion contract. Replace only the failed route, owner, or method.

A takeover packet contains the exact goal, parent and root bindings, current route position, accepted artifacts, passing dimensions, failed strategy, blockers, remaining budget, authority, next decision, and reporting destination.

## Reusable skills

Use the Recursive Skill Foundry only when a repeated mechanism is stable, independently useful, economically worth formalizing, and proven on a real forward task. Skill creation defines how to perform a recurring mechanism. It never replaces the active goal or delays the current route.

## Acceptance

The root goal closes only when every mandatory target condition and metric has evidence, the integrated experience is cohesive, the complete route is usable in objective reality, and an independent acceptance actor verifies the result against the original objective.
