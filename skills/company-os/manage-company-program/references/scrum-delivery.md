# Scrum-inspired delivery management

Apply this operating behavior to every manager outcome. This adapts Scrum Master
practices to Company OS's existing agent hierarchy; it is not a claim that the
hierarchy is a textbook Scrum Team. The manager enables delivery and removes
impediments. The designated product/decision owner retains priority and scope
accountability; workers contribute estimates and implementation choices.

Reference: [The Scrum Guide, 2020](https://scrumguides.org/scrum-guide.html), especially
Scrum Master, Sprint Goal, Daily Scrum, and Definition of Done. These practices
inform this adaptation; Company OS's native chat, budget and evidence rules govern
execution. Do not introduce a separate Scrum Master agent or duplicate PM system.

## Start a delivery cycle

Agree one sprint goal expressed as a usable result, a fixed timebox within the
remaining charter budget, and an observable Definition of Done. Use an existing
sprint when present. For a small agent task, use a bounded delivery cycle without
pretending it is a full formal Scrum sprint. Completion criteria include integration
and the relevant user-path checks, not merely a worker saying its code is finished.

Select the smallest coherent backlog slice that achieves the goal. Ask workers to
surface dependencies and uncertainty before commitments. Record a forecast, not a
guarantee. Separate ready items from blocked or unaccepted work. Limit concurrent
items to actual review/integration capacity within existing concurrency ceilings.
Prefer finishing the oldest goal-relevant work to opening another lane. Started
blocked items still count against WIP until an explicit scope/priority decision
returns them to the backlog; relabeling work does not create capacity.

Use the existing task ledger/Operate backlog and PM OS baseline when available.
Keep references in the manager's existing record; do not create a competing tracker.
A compact cycle record needs only goal, timebox, owner, selected item IDs, completion
checks, WIP limit, and next inspection. Item status must link to its native worker
thread and artifact evidence. Unknown estimates and baselines remain unknown.

## Turn each heartbeat into movement

Read current worker replies and actual artifact state. Inspect progress toward the
goal, not hours worked or volume of commentary. Ask what changed, what prevents the
next integrated result, and what concrete action will occur before the next check.
Use asynchronous updates in existing conversations; do not force ritual meetings.

On every heartbeat, make and carry out one justified delivery decision: finish or
integrate a ready slice, clear a dependency, coordinate paired repair, reduce WIP,
split an oversized item without dropping its acceptance criteria, or escalate a
specific decision outside the manager's authority. If the current plan is progressing,
keep it and schedule its next observation rather than churning assignments.
A report alone is not an intervention. If execution is impossible, name the exact
missing capability/decision and continue independently useful admitted work.

For each blocker record the affected item, evidence, person/agent who can remove it,
next action and deadline/checkpoint. At first blockage, set an escalation deadline
from the dependency critical path and remaining timebox; escalate when it expires
without resolution. Send that action to the actual thread and check
for acknowledgement. Repeated unchanged blockers must trigger a changed intervention:
obtain the missing answer, negotiate a dependency, reassign within scope, or escalate
to the executive with options, recommendation and effect on the goal. Do not merely
paste the same blocked status, create duplicate workers, or poll more aggressively.
Respect concurrency, host wait limits and sustainable budgets.

## Protect the goal and quality

When a new request arrives, compare it to the goal and remaining capacity. Put
unaccepted additions in the backlog and give the decision owner the explicit
tradeoff. Renegotiate selected scope through existing PM/charter rules when needed;
never silently remove a user requirement or lower the Definition of Done to hit a
date. If the goal becomes obsolete, request the authorized owner's decision.
Allow workers to choose the implementation within their accepted scope; intervene
on dependencies, evidence and impediments instead of dictating every keystroke.

At a missed checkpoint, inspect the cause immediately. Prefer smaller integrated
slices, a resolved dependency or targeted rework to another broad planning exercise.
Stop new starts when review is congested. A finished implementation awaiting checks
is still work in progress. Failed user-path checks return the item to repair.

## Review, improve and report upward

Demonstrate the increment to its responsible owner using actual artifacts and
relevant runtime evidence. Apply existing acceptance gates. Record what met Done,
what did not, and the effect on the goal; unfinished work is not accepted by default.
Refresh the backlog/forecast using that evidence.

At cycle close choose one concrete process improvement tied to an observed delay
or defect, with an owner and a next-cycle check. Test it next cycle; do not accumulate
retrospective promises. Track goal attainment, age of active work, blocked time and
verified completed slices where measured. Do not use tokens, message counts, task
starts or story points as individual productivity quotas.

Report to the executive: goal confidence and evidence, usable increment delivered,
oldest blocker and removal action, scope/capacity tradeoff needing a decision, and
next concrete delivery checkpoint. Continue through the same manager/worker threads.
A recurring wakeup still requires the existing host scheduling capability; writing
this cadence does not make a paused conversation run autonomously.
